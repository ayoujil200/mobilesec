1. Updated Article Text: LightGBM-Based Remediation Prioritization

MobileSec includes a machine-learning component that supports remediation
prioritization after the static analysis services have completed their work.
The role of this component is not to replace the vulnerability detectors. The
platform still relies on its specialised analysis services to identify
cryptographic misuse, exposed secrets, insecure network communication, and
certificate-related weaknesses. The LightGBM model is used at the next stage of
the pipeline, where the raw security evidence is summarised into a scan-level
feature vector and mapped to the most appropriate remediation category.

This design reflects the way security results are produced in the platform. A
single APK scan may generate findings from several services, and these findings
are not always directly comparable. For example, a scan can contain weak cipher
evidence, exposed API keys, insecure HTTP endpoints, and TLS validation issues
at the same time. Presenting these findings without prioritisation can make the
remediation process difficult, especially when many APKs are analysed in a
batch. The LightGBM module therefore acts as a decision-support layer: it learns
the relationship between the observed scan profile and the fix category that
should be prioritised first.

In the current implementation, each scan is represented by 24 numeric features
extracted from the MobileSec result collections. These features describe three
main security dimensions: cryptographic findings, secret leakage findings, and
network security findings. They include counts of weak ciphers, weak hashes,
insecure randomness, weak RSA usage, exposed API keys, passwords, tokens,
network endpoints, HTTP issues, certificate issues, total vulnerabilities, and
an aggregated severity score. The model predicts a MobileSec-specific
fix_category label, such as FIX_EXPOSED_API_KEY, FIX_INSECURE_HTTP,
FIX_CERTIFICATE_ISSUE, FIX_WEAK_CIPHER, or FIX_HARDCODED_PASSWORD.

LightGBM was selected because this learning problem is structured and tabular.
The model does not receive images, raw bytecode, or natural-language input; it
receives compact numeric descriptors derived from security analysis tools.
Gradient-boosted decision trees are well suited to this type of data because
they capture nonlinear interactions between sparse count-based features while
remaining efficient to train and deploy. LightGBM also provides probability
outputs and feature-importance values, which are useful for a software article
because they make the prioritisation step easier to inspect and explain.

The model is trained as a multiclass classifier. The objective is multiclass
classification and the optimisation metric is multi-class log loss. Since the
platform returns ranked remediation suggestions, the probability distribution
over categories is more useful than a single hard label. At inference time, the
highest-probability category is returned as the primary fix, while the top-k
categories can be used to support the recommendation service.

The training pipeline applies several safeguards before fitting the model.
First, it validates that all required feature columns and the target
fix_category column are present. Second, it filters the training data using the
label quality metadata. In the current experiment, only labels with sufficient
confidence and accepted review status were retained. Third, rare classes with
too few samples for stratified splitting are excluded. Fourth, the labels are
encoded, the numeric features are standardised, and the data is split into
training, validation, and held-out test partitions using stratification.

For the current model, the training data was obtained from the MobileSec
MongoDB-derived extracted dataset. The extracted CSV contains 1,559 labelled
rows before quality filtering. After removing low-confidence or unreviewed
labels, 1,475 rows were retained for training and evaluation. The retained
training set contains seven fix categories and 24 input features. The split used
by the implemented trainer produced 1,031 training samples, 222 validation
samples, and 222 held-out test samples.

Several conservative LightGBM configurations are evaluated during training:
balanced_regularized, minority_sensitive, simple_low_variance, and
slow_deep_regularized. The selected model is chosen on the validation set using
macro-F1 as the primary criterion, followed by balanced accuracy and ordinary
accuracy. This is important because the fix-category distribution is imbalanced:
classes such as FIX_EXPOSED_API_KEY and FIX_INSECURE_HTTP occur more often than
classes such as FIX_HARDCODED_PASSWORD or FIX_INSECURE_RANDOM. The trainer also
uses balanced sample weights so that minority categories have a stronger effect
on the loss during training.

The selected configuration for the current model is balanced_regularized. A
standard stratified hold-out split produced very high diagnostic values
(accuracy = 0.9910 and macro-F1 = 0.9868), but these values should not be used
as the main paper claim because the dataset contains repeated scan patterns and
rule-derived labels. For publication, a stricter grouped evaluation was also
performed. In this protocol, identical feature vectors are kept in the same
split, which avoids testing the model on feature patterns already seen during
training. Across 20 grouped splits, the model obtained 0.8541 accuracy, 0.8488
macro-precision, 0.8508 macro-recall, 0.8258 macro-F1, and 0.9922 top-3
accuracy. These values are more conservative and better reflect expected
generalisation on less redundant scan profiles.

The feature-importance values are also consistent with the intended behaviour
of the model. The strongest features include secrets_api_keys,
secrets_passwords, network_cert_issues, crypto_weak_cipher, crypto_medium,
secrets_tokens, severity_score, total_vulnerabilities, secrets_count, and
crypto_insecure_random. This ranking is meaningful because the model assigns
high importance to features that directly describe the remediation classes it
predicts.

The LightGBM categories should be described as MobileSec remediation categories,
not as official OWASP categories. They represent operational fix labels used by
the platform to guide remediation. These labels can be mapped to broader OWASP
MASVS domains. For example, FIX_WEAK_CIPHER and FIX_INSECURE_RANDOM are related
to cryptographic controls, FIX_INSECURE_HTTP and FIX_CERTIFICATE_ISSUE are
related to network security controls, and FIX_EXPOSED_API_KEY or
FIX_HARDCODED_PASSWORD are related to insecure credential handling and storage.
This distinction avoids claiming that the classifier predicts official OWASP
labels while still allowing the paper to connect the recommendations to
recognised mobile security standards.


2. Shorter Version for the Paper Methodology Section

MobileSec uses a LightGBM-based multiclass classifier to prioritise remediation
after the static analysis phase. The classifier consumes 24 scan-level features
extracted from the cryptographic, secret-detection, and network-analysis
services. These features encode vulnerability counts, issue types, severity
distributions, and an aggregated severity score. The model predicts a
MobileSec-specific fix category, such as exposed API key removal, HTTPS
enforcement, certificate validation repair, hardcoded password removal, or weak
cipher replacement.

The classifier is trained on the MongoDB-derived extracted dataset generated by
the MobileSec pipeline. The current extracted dataset contains 1,559 labelled
rows. After label-quality filtering, 1,475 accepted rows were retained, covering
seven remediation categories. The data was split into stratified training,
validation, and test partitions. During training, several LightGBM
configurations were compared, and the final model was selected using validation
macro-F1 as the main criterion. Balanced sample weights were used to reduce the
effect of class imbalance.

Under a stricter grouped evaluation, the final LightGBM model achieved 0.8541
accuracy, 0.8258 macro-F1, and 0.9922 top-3 accuracy on average across 20
grouped splits. The model also produced interpretable feature
importance values, with exposed-secret, certificate, cryptographic, and severity
features among the most influential predictors. These results show that the
model provides an efficient and explainable prioritisation layer for converting
heterogeneous security findings into actionable remediation categories.

4. Notes for Transparent Reporting

The article should explicitly distinguish between three different datasets or
counts:

1. The real platform scan database contains 2,125 scan records in MongoDB.
2. The APK benchmark comparison uses 283 APKs: 118 DroidBench APKs and 165
   Ghera APKs.
3. The LightGBM model was trained on 1,475 accepted labelled rows extracted
   from MobileSec scan results.

These numbers describe different parts of the evaluation and should not be
mixed. The 283 APK count belongs to the tool-comparison experiment. The 1,475
row count belongs to the LightGBM training and test evaluation. The 2,125 scan
count belongs to the broader MobileSec platform database used for real scan
aggregation.

The report-generation and SARIF rows in Table 6 also require careful wording.
For the benchmark batch, JSON reports were generated automatically for the 283
MobileSec scans. PDF generation is available on demand from the frontend, but
it was not generated as part of the automated benchmark runner. SARIF export was
not produced for the benchmark batch. Therefore, Table 5 reports MobileSec PDF
export as "On demand", JSON export as "283/283", and SARIF export as "0/283".

11. Wording for the Limitations Section

The current evaluation has two limitations that should be stated explicitly.
First, the LightGBM labels are MobileSec remediation categories derived from the
platform's available fix-suggestion and rule-based labelling logic. They are not
manual OWASP labels and should be interpreted as operational fix categories.
Second, the current LightGBM model is scan-level rather than vulnerability-level.
It predicts the dominant remediation category for an APK scan, while individual
vulnerability ranking still combines the model output with severity-based
signals. A future extension could train one instance per vulnerability and use
local evidence such as file location, detector source, CWE, severity, and
surrounding code context.


12. Final Article-Style Conclusion for the ML Part

The LightGBM module adds an explainable prioritisation layer to MobileSec. It
turns heterogeneous outputs from several security services into ranked
remediation categories, reducing the manual effort required to interpret large
scan batches. The model is lightweight enough to run inside the Dockerised
microservice architecture and produces feature-importance values that support
inspection of its decisions. In the current evaluation, the model achieved
strong held-out performance on accepted MobileSec training rows, indicating that
the extracted security features are informative for remediation prioritisation.
